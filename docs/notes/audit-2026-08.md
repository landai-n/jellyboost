#### SP-04 — A local pause outside the protocol (audio focus loss, headphones unplugged) puts the drift monitor into a permanent 1 Hz seek loop with no recovery  
**Medium** (stability, downgraded from High) — `player/src/main/kotlin/dev/jellyboost/player/syncplay/SyncPlayDriftMonitor.kt:62`

ExoPlayerHandle builds the player with handleAudioFocus = true and setHandleAudioBecomingNoisy(true) (ExoPlayerHandle.kt:127-138): a phone call, another app taking focus, or a headphone unplug pauses the underlying ExoPlayer directly, bypassing SyncPlayAwareForwardingPlayer (which only intercepts MediaSession-dispatched calls). The controller ignores PlayerEvent.IsPlayingChanged (SyncPlayController.kt:1381-1386 handles only Ready/Ended), so phase stays SyncPlayPhase.Playing(anchor) and observeAnchor keeps the monitor running. correctOnce guards only snapshot.hasEnded (line 62) — never snapshot.isPlaying — so against a paused player the drift grows ~1s per tick, exceeds MAX_DRIFT_MS within 2 ticks, and playerHandle.seekTo(expectedMillis) fires every second, forever, without ever calling play().

**Impact:** During any phone call or headphone unplug while in a playing group: the paused frame visibly jumps forward every second, a transcoded stream issues a ranged fetch/re-buffer per second indefinitely (network and server churn), and the member is silently desynced. #### SP-02 — Backing out of the player during a group-driven load makes this client skip the item for the whole group  
**Medium** (stability, downgraded from High) — `player/src/main/kotlin/dev/jellyboost/player/syncplay/SyncPlayController.kt:1292`

`reconcile` does `val loaded = runCatching { attached.loadItem(entry.itemId, queue.startPositionTicks) }.getOrElse { false }` (line 1292) and treats `false` as "this device cannot open the item" (line 1293 -> `onEntryUnplayable`). The host implementation is `PlayerViewModel.loadItem`, which runs its body in `withContext(viewModelScope.coroutineContext)` (player/src/main/kotlin/dev/jellyboost/player/ui/PlayerSyncPlayBridge.kt's host == PlayerViewModel.kt:531-554). Passing a context that carries a Job re-parents the `withContext` coroutine onto `viewModelScope`, so when the user leaves the player screen ViewModel.clear() cancels viewModelScope *before* `onCleared()` runs, `loadItem` throws CancellationException — and `runCatching` swallows CancellationException like any other Throwable. The controller's own collector coroutine (session scope) is still alive, so `onEntryUnplayable` (line 1367) proceeds: it emits `SyncPlayMessage.ItemUnavailable` and calls `api.requestNextItem(entry.playlistItemId)`.

**Impact:** A user pressing Back while the group's item is still opening (e.g. opening the player from the groups screen's "open player" affordance, or the group advancing to a new episode) silently advances the queue for every member of the group. It also mis-reports the item as unplayable and burns the one-shot `skippedSlots` guard for that slot.

**Suggested fix:** Rethrow cancellation before deciding the item is unplayable: `catch (c: CancellationException) { throw c }` / use `runCatching`-free try-catch that filters `CancellationException`, and treat a cancelled load as "nothing happened" (leave `loadedPlaylistItemId` alone, no `requestNextItem`). Separately, `PlayerViewModel.loadItem` should not pass `viewModelScope.coroutineContext` (a Job) to `withContext` — use `withContext(mainDispatcher)` and let the caller own cancellation.

> Verifier (DOWNGRADE, → Medium): The mechanism is real and I verified every link in the chain against the current tree.

#### SP-01 — Scheduler bookkeeping is written from two dispatchers: missed dedupe can re-apply commands, and `pending = null` can orphan a superseded command's cancellation  
**Medium** (stability, CONFIRMED) — `player/src/main/kotlin/dev/jellyboost/player/syncplay/SyncPlayCommandScheduler.kt:141`

schedule() runs on the commands-collector thread (Dispatchers.Default) and reads lastApplied/pendingScheduled for the dedupe and staleness checks (115-122), but both fields are written inside withContext(mainDispatcher) (136-137) with no synchronization — the identity comparison can read a stale value across threads. Separately, line 141 (`pending = null` after the withContext block) has no identity guard, unlike pendingScheduled's `=== taken` check at 136: if a completing job's post-apply resumption on the scope thread interleaves with a concurrent schedule() that has just written `pending = jobB`, the old job nulls the field, and the next schedule() then cannot cancel jobB — a superseded command survives to fire at its instant.

**Impact:** (a) A missed dedupe re-applies the server's verbatim 'client got lost' re-send: a re-seek, a re-buffer, and a fresh readiness — the exact feedback loop the applied-exactly-once guard exists to stop (STATUS.md B1/B2). (b) An orphaned superseded command applies after its replacement, jumping the player to a stale position/state that nothing corrects until the drift monitor's 2 s threshold or the next group transition.

**Suggested fix:** Guard line 141 with `if (pending === <this job's ref>) pending = null` (capture the job), and move pendingScheduled/lastApplied writes onto the same thread schedule() runs on (or confine the whole scheduler alongside the controller on a single-threaded dispatcher, applying only the playerHandle calls on main).

#### SP-03 — enterGroup replays the stashed pre-join queue unordered against live queue updates, letting a stale queue overwrite a newer one  
**Medium** (stability, CONFIRMED) — `player/src/main/kotlin/dev/jellyboost/player/syncplay/SyncPlayController.kt:618`

performJoin stashes a queue update that arrives before the join call returns (pendingQueue, onQueueChanged:1228). enterGroup sets _state to InGroup at 586 — from which moment the live group-updates collector applies any further PlayQueueUpdate directly — and only later launches the replay as a detached coroutine: `session.launch { onQueueChanged(queued) }` (618-621). There is no ordering between that launch and the collector: if the server sends a second PlayQueueUpdate right after the join (a queue edit, next-item, or the post-join state settle), the collector can apply the newer queue first and the replayed older one then overwrites _state.queue and runs reconcile against it.

**Impact:** The member loads or seeks to the stale queue's slot/startPositionTicks — the joining member lands on the wrong item or position, reports buffering/ready for a slot the group already left, and stays wrong until the next queue publication. Rare (needs two queue updates around the join instant) but permanent-until-corrected when it hits, and precisely the kind of join-window regression 5c8a6ec2 was fixing.

**Suggested fix:** Replay the pending queue inline in enterGroup before the state becomes visible to the live collector (or tag queues with lastUpdate and have onQueueChanged drop any queue older than the one already in _state — the timestamp is already on SyncPlayGroupQueue).

#### SP-05 — One failed 10 s poll hides the in-group card and its Leave button behind a full-screen error

#### DL-01 — A stalled socket wedges the download queue permanently: no read timeout and the OkHttp call is never cancelled once the body starts  
**High** (stability, CONFIRMED) — `data/downloads/src/main/kotlin/dev/jellyboost/data/downloads/di/DownloadsModule.kt:92`

The download client is built with `.readTimeout(0)` (DownloadsModule.kt:92) — no bound at all on the gap between two bytes. `FileDownloader.await()` (FileDownloader.kt:279-299) installs `continuation.invokeOnCancellation { cancel() }`, but that continuation has already resumed by the time the body is read, so nothing holds or cancels the `Call` during `writeBody`/`copy`. The copy loop only checks `coroutineContext.ensureActive()` *between* reads (FileDownloader.kt:230-231), so a blocked `input.read(buffer)` (line 232) is uninterruptible: coroutine cancellation cannot reach it, `Response.use` never unwinds, and the response is never closed. A half-open TCP connection (mobile/Wi-Fi handover, a NAT or reverse proxy dropping an idle-looking long transfer, a server killed mid-stream) therefore parks the transfer forever.

**Impact:** The item sits at N% with a live foreground notification and never fails, never retries, never reports. Worse, `DownloadQueue.drain` holds the process-wide `drainLease` mutex (DownloadQueue.kt:155,185) for the whole drain, so the queue is dead for the rest of the process: every later `ensureRunning()`/`restart()` starts a worker that blocks on the mutex while promoting itself to the foreground. `DownloadScheduler.stop()` gives up after 5 s (DownloadScheduler.kt:99-109) and returns, so `deleteAll`/`setStorageLocation` then unlink files and rows while the stalled reader is still holding and re-creating them.

**Suggested fix:** Give the download client a real read timeout (e.g. 60-120 s between bytes — that is orthogonal to total call duration and does not break long healthy transfers), and hold the `Call` in `FileDownloader.download` so the coroutine's cancellation (and the worker's stop) can `call.cancel()` during the body read, not only while awaiting the response headers.

#### DL-08 — `|| it.isExternal` marks source streams side-loaded with no merge child behind them, shifting the child-index mapping  
**Medium** (stability, CONFIRMED) — `player/src/main/kotlin/dev/jellyboost/player/resolve/LocalPlaybackResolver.kt:193`

`toAudioTracks` flags a track side-loaded when `it.index in sidecarIndices || it.isExternal` (line 193). `TrackSelectionController.selectAudio` then treats *every* `isExternal` audio track as a merge child: `sideLoaded = source.audioTracks.filter { it.isExternal }`, `sidecarChildren = 1..sideLoaded.size`, and the k-th of them is looked up as the group whose id bears merge prefix `k + 1` (`TrackSelectionController.kt:91–111`). But the merge children actually built are `LocalPlaybackMediaSource.externalAudio` = `audioSidecars` only (line 128), and `audioSidecarsOnDisk` returns `emptyList()` for a non-transcoded download (line 239).

Two concrete divergences:
1. **ORIGINAL download with an external audio stream in the source** (a `.mka` beside the video — Jellyfin lists it in `mediaStreams` with `isExternal = true`). `audioTracksInFile` returns *all* audio streams for a non-transcoded download (line 177), so the picker offers that track; `sideLoaded` is non-empty while `externalAudio` is empty, so `selectAudio` finds no group with prefix 1 and returns `false`, forcing a remote re-resolve that cannot succeed offline. Note the subtitle path *does* guard this exact case with `!transcoded && !stream.isExternal` (line 99); audio has no equivalent.
2. **Transcoded download whose baked track is itself external.** `downloadAudioStreamIndex` (`DownloadAudioSelection.kt`) returns `defaultAudioStreamIndex`, which may name an external stream. `audioTracksInFile` puts it first (line 178), and `toAudioTracks` flags it side-loaded, so `sideLoaded` becomes `[baked, sidecar0, sidecar1]` and every ordinal shifts by one: selecting the baked track resolves to merge child 1 — the *first sidecar's file* — and the last sidecar resolves to a child that does not exist.

**Impact:** Case 1: the offline picker advertises an audio language that can never be selected, and the failed selection routes to a server that is not there. Case 2: choosing the item's default/baked language plays a different language, and the highest-index sidecar becomes unselectable — the precise class of bug the merge-child contract was introduced to prevent.

**Suggested fix:** Derive the side-loaded flag from the sidecar set alone — `sideLoaded = it.index in sidecarIndices` — so the flag means "this track has a merge child" and nothing else. #### NET-01 — Reachability probe re-points the authenticated client at any host that returns 200 from /System/Info/Public — server identity is never verified  
**Medium** (security, downgraded from High) — `core/network/src/main/kotlin/dev/jellyboost/core/network/connectivity/ServerProbeApi.kt:52`

`SdkServerProbeApi.isReachable` (ServerProbeApi.kt:45-52) treats *any* HTTP 200 from `getPublicSystemInfo()` as "our server": it discards the response body and never compares `PublicSystemInfo.id` to the signed-in `session.serverId`. `ServerReachabilityProbe` then acts on that verdict — ServerReachabilityProbe.kt:53-60 loops the candidates and calls `apiClientProvider.useAddress(address)`, which is explicitly documented (ApiClientProvider.kt:88-99) as re-pointing the shared `ApiClient` **keeping the current credentials** (`apiClient.update(baseUrl = baseUrl)`). Candidates come from `serverDao.getAddresses(session.serverId)` (ServerReachabilityProbe.kt:73-80) — i.e. the literal address string recorded at sign-in (AuthRepository.kt:287-289), which for self-hosted Jellyfin is routinely a private LAN address (the app's own placeholder is `http://192.168.1.10:8096`, core/ui/.../JellyfinTextField.kt:209). The probe is not user-initiated: `ConnectionStateProvider` fires it on every network change, on session change, on resume and on a re-probe timer (ConnectionStateProvider.kt:129-131). `network_security_config.xml:11-13` permits cleartext to every host, so no TLS check intervenes either. Contrast setup-time resolution, which *does* extract and check the server id (ServerDiscoveryRepository.kt:88-93) — the identity concept exists, it is just not applied on the reconnect path.

**Impact:** A user who signed in at home on `http://192.168.1.10:8096` and later joins any other network where that address is reachable (192.168.1.x is the default range of most consumer routers) will have the app silently re-point at whatever answers there. An attacker on that LAN only needs a stub that replies 200 to `GET /System/Info/Public`. From that moment every authenticated request carries `Authorization: MediaBrowser ... Token="<access token>"` to the attacker: the SDK client, `JellyfinAuthInterceptor` (whose allow-host is derived from the now-attacker `apiClient.baseUrl`, JellyfinAuthInterceptor.kt:30-34), `FileDownloader.authorizationHeader()` (FileDownloader.kt:158, 251-257) and the SyncPlay websocket (OkHttpSyncPlaySocket.kt:298-311). The Jellyfin access token is long-lived and unscoped, so disclosure is full account compromise. The switch is also sticky: `candidateAddresses()` puts the current `baseUrl` first, so the attacker host wins every subsequent probe for the rest of the app session, and browsing/search/playback-report traffic goes there too.

**Suggested fix:** Have `ServerProbeApi.isReachable` return the probed server's id (the response content is already fetched) and make `ServerReachabilityProbe` accept an address only when that id equals `session.serverId`; treat a mismatch as unreachable and log it. Keep `useAddress` reachable only from that verified path.
